# core/ — Rust núcleo

The núcleo binary crate (`nucleos-core`). Owns the local HTTP API, the SQLite datastore,
secrets access, sidecar supervision, and the CLI-wrap agent loop. Entrypoint: `src/main.rs`
(pure startup orchestration — no domain logic of its own).

**Foundation status: complete.** Every module in spec §3.2's map is implemented and green:
`cargo test -p nucleos-core` = 1128 passed + 3 ignored (the ignored ones touch the real OS Credential
Manager / Task Scheduler; run with `-- --include-ignored` on an interactive desktop session).
> A count in a document is a claim that goes stale without anybody editing it — this line read
> `276 passed + 2 ignored` for long enough that four times as many tests had been written under it.
> Treat it as the order of magnitude it is, and `cargo test -p nucleos-core` as the authority.


## Module map — the structural invariant (spec §3.2)

**One file per concern; no module mixes HTTP transport with domain logic.** This is the load-bearing
structural rule. Every current file maps 1:1 to spec §3.2 and it MUST stay that way — this table is
the contract, not a snapshot.

| File | Responsibility |
|---|---|
| `main.rs` | Startup orchestration ONLY: logging → autostart → storage → reconcile orphaned runs/stranded approvals/orphaned worktrees → secrets/token → model config → `AppState` → HTTP router → sidecar + scheduler + repo-poller + worktree-GC background tasks → serve. No business logic. |
| `logging.rs` | `tracing` subscriber (rotating daily file + stdout), initialized first to catch a failed startup. |
| `autostart.rs` | Self-registers OS autostart at login, independent of the shell: a Windows Scheduled Task (`LogonTrigger` + `RestartOnFailure`), a macOS LaunchAgent, or on Linux a systemd user unit or an XDG autostart entry (one Linux backend at a time). Registering never starts a second daemon. Non-fatal on failure. |
| `storage.rs` | SQLite pool + WAL + `sqlx::migrate!`. Knows the storage *mechanism* only — never a table's meaning. |
| `backup.rs` | Backup files: takes a consistent snapshot, verifies one, and stages a restore for the next startup to apply. |
| `auth.rs` | Local token generation + the bearer-token middleware on protected routes. |
| `attention.rs` | The expiring owner-presence brake: explicit foreground-client heartbeats plus in-flight run handles, scoped globally or per project. Missing heartbeats allow, broken reads fail closed, and the lease self-clears without manual reset. Judges whether attention permits a new run; never starts or schedules one. |
| `state.rs` | `AppState` — the ONLY place cross-cutting deps join (token, pool, runner, in-flight run handles, run timeout, workflow library root). `workflow_library: Option<PathBuf>` follows the `files_root` precedent and is deliberately NOT an environment variable: a process-global would make two tests with different libraries race, and `set_var` is `unsafe` in edition 2024. Resolved once at startup, `None` meaning this machine has no library rather than an error. |
| `runner.rs` | The núcleo↔**model** boundary. `CommandRunner` trait + `ClaudeCliRunner` (real CLI; honours `NUCLEOS_CLAUDE_BIN`, streams `stream-json`, `kill_on_drop`) + `FakeCommandRunner`, the per-run TURN CEILING (`turns_from_line`/`over_turn_ceiling`/`TURN_CEILING_EXIT_CODE`, counted from the transcript because CLI 2.1.198 has no `--max-turns`; enforced in BOTH runner bodies), plus the loopback Ollama path: `OllamaRunner` (tool-free local triage, its own sampling grammar) and `ollama_chat`, the shared chat-endpoint call that any local-model consumer uses so there is only ever one HTTP client pointed at Ollama. |
| `openai_compatible.rs` | The núcleo↔**OpenAI-compatible chat wire** boundary: `OpenAiCompatibleChat`, a second `local_agent::LocalChat` implementation beside `runner.rs`'s `OllamaChat`, so the same tool loop can be pointed at any endpoint that speaks `/chat/completions` — a hosted provider (OpenRouter today, at `OPENROUTER_BASE_URL`) or a server on this machine answering the same route — instead of the loopback one. Reads a response into the same message shape the Ollama path already produces — `content` and/or `tool_calls` — so `local_agent::tool_calls`'s argument normalisation needs no second copy for this provider. The key is passed in, never read from a config file and never from the Credential Manager by this module itself: `secrets.rs` is the one thing that touches the keyring, and construction refuses outright when no key was found, rather than building a client whose first request would come back 401. Knows nothing about Ollama's own `/api/chat` shape, nothing about which model a caller should choose, and nothing about routing between the two providers — that choice belongs to whoever constructs one. |
| `transcribe.rs` | The núcleo↔STT boundary: `Transcriber` trait + `CommandTranscriber` (spawns the operator's command, audio path appended last, duration-derived deadline, output ceiling that **errors** rather than clipping) + `FakeTranscriber`. Owns the temp-recording RAII guard, so "transcribe then delete" survives a dropped request. Knows nothing about what a transcript means. |
| `speak.rs` | The núcleo↔**TTS** boundary: where text becomes audio, and where a third-party program is given a chance to misbehave. The mirror of `transcribe.rs` down to the shape of its guards — a trait, a real implementation that spawns whatever the operator configured, and a fake for tests. Keeping it in its own file is what lets the voice domain in `voice.rs` stay ignorant of processes and deadlines, and what lets a cloned voice arrive later as a second `impl` rather than as a rewrite. Knows nothing about what is being said. |
| `speed.rs` | The speed profile's daemon half only: the NAME (`Speed`: `normal`, `fast`, `thorough`) and the CAPACITY it buys -- `team_multiplier` and `team_width`, the rule that widens a department round under `fast`, never raises a serial team and never passes `team::MAX_PARALLEL_CEILING`. What a speed means for the process (reasoning effort, fast path, review, waves) belongs to the workflow, which the daemon does not read: no `.ai/workflow/*` file is consulted and no table is mirrored. The daemon hands every session it launches its two facts through `Capacity::env` -- `WORKFLOW_SPEED` and `WORKFLOW_PARALLEL_CEILING`, neutral names on purpose, never `NUCLEOS_*` -- and every ceiling check stays where it was, so a child asking for more gets no more. `normal` is today's behaviour, pinned by test. Knows nothing about databases or HTTP. |
| `runs.rs` | `/runs` HTTP handlers + the runs domain (create/get/cancel, `create_run_inner` for worktree/shadow modes, `resume_approved_run` for an approved proposal's resume, `finalize_termination`, `reconcile_orphaned_runs` + `reconcile_stranded_approvals` on startup). `run_env` is the one place a launched session's environment is assembled, for runs, job nodes, department members, council seats and assistant turns alike, which is where `speed::Capacity::env` is added. Owns its own runs SQL so `storage.rs` stays table-agnostic. |
| `run_stop.rs` | "Porque parou": the pure, DB-free half of `GET /runs/{id}/stop` (spec §7). Derives the response `kind` from a run's `status` off `runs.rs`'s own `ENDED_RUN_STATUSES`/`TERMINAL_RUN_STATUSES` rather than a second list; derives the timeout verdict — `silence` or `undetermined`, **never** `wall`, spec §6 — from elapsed time against the two independent ceilings, reusing `runs.rs`'s `runs_unattended`/`run_timeout_for_mode`/`progress_timeout_for_mode` rather than recomputing `base * multiplier` a second time; and holds the response's own types. Reading the run row and the `shadow_decisions` rows stays in the HTTP handler, which is thin and calls this module to turn what it read into a response. |
| `handoff.rs` | Context handoffs recorded as an auditable event plus a successor run, so a run that hit context pressure can be shown to have continued rather than having its past rewritten. Never rewrites an existing run's history. |
| `job.rs` | The job state machine: a sequence of runs over one shared worktree, so autonomous work is not capped by a single context window. Nodes run `plan -> implement*N -> gate -> review`, each with a fresh window, sharing state through the worktree on disk rather than a transcript. `next_step` is PURE and holds every interesting decision (where does a red gate leave the queue, where does a resume pick up), so they are table tests with no database, worktree or subprocess -- the same split `classifier.rs` has from `hooks.rs`. Also OWNS STARTING a job: `resolve_start` is the pure half (a job requires active mode -- shadow is plan-only and its plan node could not write the plan.json the queue comes from), `start` is the half that writes the row and provisions the worktree. Both moved here from `scheduler.rs` when `POST /jobs` needed the same sequence; the scheduler now only translates a fired rule into a `StartRequest`. A green gate takes a CHECKPOINT (`job_items.checkpoint_sha`); a red one first spends the item's RETRY BUDGET (`jobs.gate_retries`, counted in `job_items.gate_attempts`) — the tree is left exactly as the rejected attempt made it and the same ordinal is implemented again with the gate's own output in its prompt, because §5.4 keeps the second node from ever seeing the first one's session, so a node that cannot see what it broke spends a whole run rediscovering what the gate already printed. Only once the budget is spent does the revert happen, to the previous item's footing, so a broken item still does not end the night — it is undone and the queue carries on, with `ending()` still reporting the job `gate_failed` at the end. Retriability is DERIVED and never stored: the row says `gate_failed` either way, `item_state_from` reads that status against the two counts, and `ItemState::claimable_as` is the one inverse of it — which is what lets `spawn_node`'s compare-and-swap name the status it expects without the SQL recomputing `gate_attempts <= gate_retries` in a second dialect. `GateErrored` deliberately still stops everything: a gate that would not run measured nothing, and continuing past silence is what the gate exists to prevent. |
| `presets.rs` | Saved run configurations (create/list/get/update/delete), owning the `run_presets` table and preserving the same launch fields as `runs::CreateRunRequest`; never starts a run itself. |
| `hooks.rs` | `/hooks/pretooluse-decision` handler — **the real risk-classifier integration (§8.2)**: routes every call through `classifier::classify` (`CLASSIFIER_VERSION = 14`), records `shadow_decisions` for shadow/worktree runs, enforces the assistant/shadow-mode brakes, consumes single-use action grants, and turns a `pending_approval` into an active termination (`runs::finalize_termination`) plus an action-approval proposal. Owns none of that logic itself — classification lives in `classifier.rs`, proposal storage in `proposals.rs` — this module only wires them together. `pause_for_approval` now has TWO outcomes and the split is on whether the run OWNS AN ITEM (`put_the_item_down`, not `runs.job_id`): an item's node marks it `skipped`, lifts its own pause to `interrupted`, reverts the tree and lets the job carry on; everything else — an ordinary run, and equally a job's plan or review node, which own no item — parks and asks. The order of writes in `skip_the_item` is the safety argument — the mark goes first, because an item left `running` in a job nobody drives makes `next_step` answer `Wait` for ever and no later pass rescues it. |
| `secrets.rs` | Thin OS-Credential-Manager wrapper — no home-grown crypto. |
| `sidecar.rs` | Generic sidecar supervisor (spawn/wait/restart) — reusable for any future Go sidecar. Owns the process-global registry of what it last saw of each child, which is what `GET /sidecars` lists and what `health.rs` grades a readiness row from. It reports the OS's `ErrorKind` and never a `FailureCategory`: the vocabulary a person reads is `health.rs`'s to choose, and keeping that translation in one place is what stops one spawn failure being described two ways. |
| `config.rs` | Model pinning (`~/.nucleos/nucleos-models.yaml`) + the typed per-project `autopilot.yaml` reader (`load_schedule_rules(machine_root, project_id)` → `AutopilotRules { schedules, repo_triggers }`, from `~/.nucleos/projects/<id>/`) read by `scheduler.rs`/`repo_trigger.rs`. Both fall back to defaults when the file is absent but error on malformed YAML rather than guessing. |
| `http.rs` | axum router + CORS assembly — the ONLY module that knows the transport is HTTP. |
| `health.rs` | Bounded, credential-safe subsystem readiness readout (SQLite, CLI binary, Credential Manager, worktree disk and the supervised sidecars). Sidecar rows report LIVENESS, read from `sidecar.rs`'s registry through a pure function; the one limit left is that a running-but-wedged child reads ok, because the supervisor watches processes and not progress. `cli_binary` and `voice_transcriber` name no resident process, so they are executed — behind a 60s cache refreshed off the request path, because the readout is budgeted at one second and the shell polls it every three. `record_breach_intent` (off unless a project's rules set `health_breach_intent`, and not yet wired to a trigger) writes a line to that project's feed — never a ledger in the project's `.ai/`, which is the AI workflow's. |
| `command_reader.rs` | PURE: the one reader of a shell line, for the two callers that must understand one — `classifier.rs` (may this run continue?) and `vcs.rs` (is there a git operation in here?). Quote-aware, heredoc-aware and here-string-aware for `Shell::Posix`; a PowerShell line keeps the eager, quote-blind reading because its backtick escape and `@'...'@` here-strings are a second grammar this does not model, and splitting too much is the safe direction. TWO ENTRY POINTS on one grammar, and the asymmetry is deliberate: `read` REFUSES the forms that are not a sequence (`$(`, backtick, a lone `&`), because a caller deciding whether to ALLOW must stop at a line it cannot read; `segments` never refuses, because a caller asking whether a line CONTAINS a merge most needs to keep scanning the line it cannot fully read — refusing there would hand back nothing and read as `no merge here`. Parentheses separate for the queue (`(git merge x)` is a merge) and NOT for the classifier (`find . \( -name a -o -name b \)` is one command, and cutting it would park lines that pass today). Says only WHERE the boundaries are, never whether anything is permitted. |
| `classifier.rs` | Pure, deterministic lexical action classifier (`classify`, `CLASSIFIER_VERSION = 14`): tool name + input + cwd + the owner's GitHub policy in, `allow`/`deny`/`pending_approval` + an `action_class` out. No I/O, no DB, no knowledge of run state. **THREE production callers, not one** — `hooks.rs` twice (`pretooluse_decision`, `rooted_decision`) and `runs.rs` once (`resume_approved_run`) — and all three must be handed the policy of the SAME PROJECT, or the hook and the resume answer differently about one command line. "The same `Policy` off `AppState`" is what that used to say, and `Policy::for_project` ended it: the value handed to a decision is now the machine default from `~/.nucleos/github.yaml` with that project's declared operations laid over it, read from the database at the moment of the decision and thrown away after — so the policy is a table read twice at two moments, exactly as the shell rules are. It can turn a `pending_approval` into an `allow` for a `gh` read it would not otherwise recognise, and it can do nothing else -- it cannot lift a `deny` and cannot reach the approval list. `shell_form_is_readable` is split out from `is_safe_command` so the owner's list clears exactly the shape guards the compiled list clears. |
| `autopilot.rs` | Per-project `Mode` (off/shadow/active) + activation prerequisites (git repo, the project onboarded to NucleOS — a marker in its state directory, see `onboarding.rs`, and no longer anything of the `.ai` workflow's — a registered PreToolUse hook) + the global and per-scope kill switches + the project roster the shell polls. Decides *whether* a project may act autonomously; never whether one specific action is safe (`classifier.rs`) and never starts a run itself. |
| `judge.rs` | The autopilot's judge (spec `2026-09-26-autopilot-modo-juiz-design.md`): a MODEL given the chance to decide one tool call the classifier left open in an AUTONOMOUS run, with the Jev as the only occupant. **Not the chat judge** of `project_policy::judge` / table `project_judge` (0129) / `/projects/{id}/judge` / `hooks.rs`'s `judge_for`: that one picks the model that answers a conversation's `auto` permission rung; this one sits at the end of the autopilot's hook and its setting is `autopilot_state.judge`. PURE half here: the questions as a list (`JUDGE_QUESTIONS`, D8), `min` and the three asymmetric bands (D7), thresholds that only tighten, `JUDGE_MAY_NOT_ALLOW` and `judge_may_allow` (D5 — the guards live in `classifier.rs`, beside the normalisation they reuse), which calls are asked (D4/D6), and the `state` (D9). I/O half: `prepare` / `ask` / `record` under ONE `JUDGE_DEADLINE`, the row written off the response path (D10/D12); every failure — deadline, HTTP, bad JSON, a missing probability, no key, no permit, an unreadable `.ai/autopilot.yaml` — leaves the classifier to decide alone. `judge/client.rs` holds the post (`Judge::ask(state, questions)`, answers keyed by question) and `JevJudge` (one POST to TypeSafe, key `typesafe-api-key` read per call from the keyring); `judge/review.rs` (from chunk 7) holds the review queue and readiness. The judge never changes a `Classification`. Spec B reuses `judge_may_allow`, `JUDGE_QUESTIONS` and the deadline rather than copying them. Spec B lives beside it: judge/resolve.rs (the resolver's four questions, three events, fixed outcomes and caution order, D10 eligibility, and its judge_resolutions rows — E1 and E3), judge/correction.rs (E4) and judge/resolve_review.rs (its review queue and readiness). |
| `shadow.rs` | Shadow-mode decision log (`record_decision`) + the human-review scoreboard + the §8.2 promotion-readiness arithmetic (`class_ready`/`promotable`/`shadow_readiness`) — the single source of truth both the roster and the promote button read. Records what the classifier *would* have done; never itself allows or blocks a tool call. Every row carries TWO identifiers and they mean different things: `classifier_version` is the CODE, and `policy_digest` (0089) is the CONFIGURATION -- from version 10 part of the policy lives in `~/.nucleos/github.yaml`, in no repository, so two machines on one version can decide the same `gh` line differently, and since `Policy::for_project` part of it lives in `project_github_ops`, so two PROJECTS on one machine can too. The digest recorded here is the effective policy's, the project's included; a project that declared nothing hashes to the machine's own byte for byte, deliberately, so that laying an empty overlay over it does not renumber every row already in the table. The reader COUNTS distinct digests and deliberately does NOT group by them: grouping would fragment the sample, and with `READINESS_MIN_REVIEWED = 10` every edit of that file would restart ten reviews of progress. The count goes into a `tracing` warning and not into the tuple, because the shell reads `classes_ready`/`promotable` off the daemon and a fourth number changes every consumer. |
| `proposals.rs` | Action-approval proposals (create/get/list/transition/reject) + their audit trail (`proposal_events`) + single-use action grants that authorize an approved resume's next matching tool call. Owns proposal state only — `hooks.rs` decides when to create one, `runs.rs` decides how a resume actually restarts the CLI. `github-action` is the seventh kind and the only one whose approval ACTS on the approval path itself (`github::approve_proposed_operation`) rather than resuming a run or waiting for a tick -- a synchronous pillar has no later pass to be picked up on, so without that the button would approve nothing; it claims the row BEFORE running `gh`, because the other order trades a readable row for a comment posted twice. `skipped-item` is the fourth kind and the only one whose approval resumes nothing — `list_pending` filters it out for that reason. The grant's `consumed_at` stamp is also the ONLY record of whether a resume did what it was resumed for: both outcomes end `completed` with exit 0, and `unconsumed_grant` is what lets `runs.rs` put a `resume_did_not_act` line in the feed instead of letting a run that refused its instruction read as success. |
| `budget.rs` | The shared autonomy budget: window/hourly spend computed from `runs` (deduping resumed sessions, time-approximating unmeasured cost) against a configurable limit. Fails closed — any read error pauses new starts rather than allowing them. Judges whether spend allows a new run; never which run to block or how. |
| `token_efficiency.rs` | Watches what runs spend per unit of work and says so when the answer stops making sense: a prompt large enough to cache that read and wrote nothing, a run past the handoff ceiling with no successor, turns spent arriving at a failure, a total far above its own recent median. **Observation only** — never pauses a run, never touches `BudgetDecision`, because braking on uncalibrated thresholds would stop real work on a guess. Sits beside `budget.rs` as the reader that telemetry has lacked since 0031, where `budget.rs` loads the same counts and must mark them dead. `evaluate` is PURE and holds the whole judgement, returning a THREE-state verdict per signal: `Quiet` is evidence and may reset a streak, `Undecidable` (missing measure, or the signal does not apply to this kind of run) leaves the row untouched — collapsing the two would let unmeasurable runs erase a real regression, and on a Codex daemon no cache streak could ever accumulate. Reports only what the daemon does NOT already answer: chats rotate and other modes hand off, so the context signal names the handoff failing rather than the swelling, and there is deliberately no prompt-to-output ratio because the `result` event is a cumulative session total. Half the module is suppression, because a feed row IS a notification (`notify.rs`) — the streak lives in `efficiency_signals` (0067) keyed by project AND mode (the population its baseline uses), advanced in one statement, and the right to speak is claimed by compare-and-swap on `last_alerted_at` so two runs finishing together produce one ping. |
| `wip.rs` | The per-project work-in-progress brake: caps how many proposals may sit unreviewed before autonomy stops starting new work for that project. Self-clearing (one human review lifts it) and fails closed like `budget.rs`, but throttles on review backlog, not spend. Counts `action-approval` and NOT `skipped-item`: one is work done waiting to be looked at (what the limit is for), the other is work not done waiting on a decision. Conflating them closes autonomy at the third skipped item of a night. |
| `scheduler.rs` | The 30s anacron tick over the cron rules from `config.rs` (`due_rules`): runs through `runs::create_run_inner`, and a window missed past `CATCH_UP_GRACE_MINUTES` demoted to a plan-only shadow run with a re-triage preamble. Defines no rule itself. |
| `team.rs` | Departments: a director agent that plans, specialists that answer, and a folder that is the delivery. Decides the SHAPE of the work -- roster, rounds, replanning, folder index -- and nothing that executes it. **Everything needed to resume a run is in the DATABASE and nothing is in memory**: a pass is `team_tick`, which reads the live runs and moves each as far as it can this second, and a subprocess landing is discovered by reading its `runs` row rather than by awaiting a task -- which is what makes a daemon restart mid-round a non-event instead of a recovery procedure. Its loop is its own rather than the scheduler's because a pass launches up to `max_parallel` subprocesses and writes files at a cadence nothing else here shares. One `runs.mode` for director and specialist alike, because everything that reads it asks the same question; which role a run played is `team_items`' answer. Never how one talks to a model (`runner.rs`), when there is money (`budget.rs`), who is who (`auth.rs`), or what a tool does to a turn (`hooks.rs`, `mcp_tools.rs`). |
| `team_notes.rs` | Words one member of a department leaves for another: the `team_notes` SQL (`leave`, `pending`, `undelivered`, `count_for_run`, `mark_delivered`, `delete_for_run`) and the PURE `render` that turns a colleague's queued notes into the paragraph a node's prompt carries. The sibling of `notes.rs` with the AUTHOR changed, and the change that module's header reserved and declined to make. **The steering channel is refused here for a structural reason and not a political one**: `team::spawn_agent` passes `messages: None`, so the runner writes the opening prompt and closes stdin and nothing is listening — and a specialist made to listen would not finish by answering but by TIMEOUT, recorded as a failure, since a `stream-json` CLI reads until stdin closes; the registry of live channels is in memory besides, against a module whose first line is that nothing is. **The governance answer lives here: writing a note is `WritesOwn` and READING one taints.** Six of the eight `TEAM_TOOLS` are `ReadsUntrusted`, so `Acts` would mean a specialist that read one page could never tell a colleague what it found — a sibling tool once made this exact trade for this exact reason. The untrusted text travels WITH the words instead of being refused at the source, and the blast radius is bounded by `TEAM_TOOLS` itself, because a note lands on another node of the same department whose only power is to ask. Addressed by `agents.id` and never by `team_items.ordinal`, which the replan renumbers. **It does NOT decide when a node runs** — `team.rs` owns that, and a note is marked delivered only once the run carrying it exists, because one spent on a node that never started is lost with nothing anywhere saying so; `pending` is a READ and never a claim, for the same reason. |
| `team_trigger.rs` | What starts a department when nobody is asking. Its own module rather than seven hundred more lines in `team.rs`, and NOT a branch in `scheduler_tick`: that loop is keyed on `(project_id, project_root, project_mode)` and everything after depends on all three -- the project's `autopilot.yaml`, `wip_permits_new_run`, `last_head_sha` -- and a department has none of them and will get none, because it works over a FOLDER and not a repository. What is reused is only what is pure and project-blind (`next_fire`, `rule_timezone`). Three governance decisions live here rather than in mechanics: the owner's attention brake is deliberately NOT consulted, the spend ceiling stops being per-run and becomes per-TREE (`tree_has_room`), and a chain is braked twice -- statically when the rule is written and dynamically while it runs (`closes_a_cycle`, `MAX_TRIGGER_DEPTH`). |
| `repo_trigger.rs` | The slower (5-minute) poller: watches configured branches for a moved SHA and fires a run the same way the scheduler does, arming first-seen triggers without firing. Shares the scheduler's kill-switch/budget/WIP gates but runs on its own cadence — `git fetch` is too network-heavy for the 30s tick. |
| `calendar.rs` | The calendar pillar's domain. (Row added when master's modules met this map; see the note at the end of this table.) |
| `mailsend.rs` | Outbound mail submission. (Row added when master's modules met this map.) |
| `notify.rs` | Notification delivery. (Row added when master's modules met this map.) |
| `notify_policy.rs` | Whether a feed kind may reach a channel at all — the family/kind selection policy: `Rule`, `Policy`, `validate` (pure, five refusals), `load`/`replace` (transactional substitute, never merge) and `observed_kinds` (`DISTINCT` over the feed's 90-day retention window). Guards, validates and observes only; resolving a policy against one feed row is the sidecar's job, not this module's. Distinct from `notify.rs`, which decides WHEN a notification goes out rather than WHETHER it is wanted. |
| `recurrence.rs` | Recurring-event expansion. (Row added when master's modules met this map.) |
| `trust.rs` | **Pure.** Whether a web page's text may reach a privileged agent as written: `decide(requested, final, requester, allowlist)` -> `Raw`/`Quarantined` plus the RULE that decided. No I/O, no DB, no run state. Trust NEVER travels up — an unknown host redirecting INTO the allowlist gains nothing, because the owner chose the first URL and not the second. Same split from its callers that `classifier.rs` and `priority.rs` have. |
| `vcs.rs` | The shared-state git/`gh` queue: typed requests, FIFO admission, the one-running-per-repository claim, tickets, and the background worker that drains every repository. Locks on the **repository key** rather than a project label, so two projects over one repository share a queue — `resolve_repo` is the single production path from a project id to a `ResolvedRepo` (id + root + key, private fields, no way to make them disagree), and it asks `git_exec::repo_key` for the key rather than computing one. Also retires requests whose submitting run has already ended, from both directions: `cancel_for_run` immediately, `reap_requests_of_ended_runs` before every claim. Owns the `vcs_requests` table's SQL. Decides WHEN an operation runs and records how it ended; never whether the actor was allowed to ask (`autopilot.rs`/`budget.rs`/`wip.rs`/`proposals.rs`), never what a merge should contain, and never how to run git (`git_exec.rs`). |
| `resolver.rs` | The half of the conflict resolver that STARTS one: a 60s loop that finds an `escalated` merge nobody has attempted, has `runs::create_resolution_run` stage the conflict in a worktree born on the merge's target, and hands that to an agent. Lives outside `vcs.rs` because the queue's executor holds a pool and a repository lock, not an `AppState` — and should not hold the lock for as long as an agent takes; the queue escalates and lets go, this picks the conflict up afterwards. ## Autopilot extends, it does NOT restructure (spec §3.2 / §9)

The next pillar ADDS modules; it must not rewrite the map above. The seams are already in place —
build against them, don't reshape them:

- **Risk classifier** → replaces the stub inside `hooks.rs`. The payload already carries `run_id`,
  validated against in-flight runs; `pending_approval` already drives active termination.
- **Approval-pause / resume** → reuses `runs::finalize_termination` (the atomic-handle arbiter) plus
  the `session_id` / `cost_usd` columns already on `runs` (captured early, so a paused run is resumable).
- **Per-project rules** → landed as `config::load_schedule_rules` (typed `autopilot.yaml` reader,
  keyed by project id under `~/.nucleos/projects/`, driven by `scheduler.rs` / `repo_trigger.rs`) + the `project_id` / `cwd` columns on `runs`.
  The untyped `discover_autopilot_config` this line used to name was superseded and is gone.
- **New tables** (`feed`, `proposals`, `budget_ledger`, …) → a new numbered migration under
  `migrations/` **and a new domain module each, owning its own SQL** (the `runs.rs` pattern) — never
  bloat `storage.rs`, which stays table-agnostic.
- **New cross-cutting deps** → add a field to `state.rs`'s `AppState`, nowhere else.

Rule of thumb: a new concern = a new file (+ its migration), wired in `main.rs` and routed in
`http.rs`. If a change would make one module know about another's transport internals or another
table's SQL, **stop** — that coupling is exactly the drift this map exists to prevent.

## Cancellation safety — the invariant that keeps being rediscovered

A dropped future stops at its last `.await` and never runs another line. Two things drop futures
here, and they are one mechanism in two costumes: `abort()` on a run's task
(`runs::finalize_termination`, reached by `/cancel` and by a `pending_approval` pause), and a client
disconnecting, which cancels the request it was making. Cleanup or follow-up written as statements
after an `.await` is therefore not cleanup — it is happy-path-only code.

It matters more here than in most services because of
`one_open_worktree_run_per_project` (migration 0009): a run stranded at `running` or
`awaiting_approval` blocks *every* later worktree run for that project, and only a daemon restart
reconciles `running`. A dropped request is not a lost reply, it is a jammed project.

Three rules, each with a worked example in the tree:

- **Own a resource with a guard, built before the task and captured by it — never inside.** See
  `assistant::ChatSlot` / `TurnGuard` and `runs::Registration`. A task aborted before its first poll
  drops its captured state without running a line of the body, so a guard constructed inside would
  never exist at all; a captured one is dropped either way. (A type implementing `Drop` is captured
  whole, so RFC-2229 precise capture cannot split it.)
- **A handler that mutates durable state across awaits goes through `http::uncancellable`.** Awaiting
  the JoinHandle leaves the response exactly as it was; dropping a JoinHandle only detaches its task.
- **Never sequence an irreversible act before the record that makes it actionable**, unless the pair
  is uncancellable together. `hooks::pause_for_approval` is the case that bites hardest: terminating
  a run kills the CLI whose hook script owns the very connection being answered.

  It now has **two** sides past that `.await`, and they order their writes differently because what
  they cannot afford to lose is different. An ordinary run terminates, records the proposal, and
  ROLLS THE PAUSE BACK if that write fails — a run parked with nothing to approve holds migration
  0009's index and jams the project. A job's node (`skip_the_item`) marks its item `skipped` FIRST
  and rolls nothing back: an item left `running` in a job nobody drives makes `next_step` answer
  `Wait` for ever, where a skipped item missing its proposal is only a reminder nobody gets. Same
  hazard, opposite worst case, so the order is opposite too.

  **Which side a run takes is decided by that mark, not by `job_id`.** A job's plan node runs before
  the queue exists and its review node runs after every item — both carry a `job_id` and neither owns
  an item, so `put_the_item_down` answers `false` and they park and ask like any other run. Branching
  on `job_id` alone left them terminated with no proposal: the exact state the rollback above exists
  to prevent, found by dogfooding on 2026-08-07 and not by the tests, which built their item by hand.

  **And a skip must clear `runs.status` as well as its own record**, or the job stops one step later
  for a different reason. `awaiting_approval` stops a job twice over: `job::node_awaiting_approval`
  parks the whole job on any run holding it, and migration 0009's index counts it as an open worktree
  slot, so the next item cannot start either. `skip_the_item` writes `interrupted` — the same verdict
  `reconcile_stranded_approvals` would write at the next startup — after the item's mark, because
  `job::reconcile_nodes` would read a still-`running` item whose run has left flight as `failed`.

## Constraints

- **This crate is the ONLY writer of SQLite.** Sidecars never open the DB file — they talk to the local HTTP API.
- **Wrap the existing agent CLI; never reimplement the agent loop** (spec §3.1).
- **Secrets go through the OS Credential Manager** (`secrets.rs`) — no own crypto, no plaintext secrets
  on disk (the daemon token included, since Chunk 1 Task 5).
- Bind the local API to **localhost** and guard it with the bearer token (spec §3.3–§3.4).
